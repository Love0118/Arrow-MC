# Rust 이식 설계 초안

이 문서는 구현 전 설계 기준입니다. 아래 경계는 논리적 책임이며, 아직 Rust crate나 trait로 구현하지 않았습니다.
첫 기능에 필요한 경계부터 코드로 만들고 실제 의존 관계가 생길 때 crate를 분리합니다.

## 책임과 의존 방향

| 영역 | 책임 | 의존 규칙 |
| --- | --- | --- |
| 공통 값·연산 | 좌표, 식별자, 수치·비트 연산, 시간 단위, RNG | 네트워크·파일·비동기 런타임에 의존하지 않음 |
| 게임 상태·규칙 | 월드·청크·블록·엔티티 상태, 이벤트와 tick 전이, AI | 공통 값과 명시적인 상태 접근 경계에 의존 |
| 서버 실행 조정 | 세션·월드 수명, tick 스케줄, 명령 실행, 입출력 결과 반영 | 게임 규칙을 호출하며 변경 적용 순서를 소유 |
| 외부 입출력 | 프로토콜 codec, 연결, 인증, 월드 저장, 설정 | 게임 내부 자료 구조를 wire/storage 형식과 구분 |
| 검증 도구 | Java 대조 실행, 상태 스냅샷, 재현 시나리오, 벤치마크 | 제품 코드가 검증 도구에 의존하지 않음 |

게임 로직에 `async`, 소켓, 파일 접근을 기계적으로 퍼뜨리지 않습니다. 외부 결과는 정해진 tick 경계에서 적용하고,
초기에는 관찰 가능한 변경 순서를 명확히 유지합니다. 병렬 tick은 순서·소유권·결정성 검증 후 도입합니다.
Pumpkin의 `Arc`·락 구조나 병렬화 방식을 프로젝트 전체 구조로 그대로 복제하지 않습니다.

## 기계적 번역 절차

1. 잠금 파일의 Java 버전과 정확한 클래스·메서드, 읽기/쓰기 상태와 호출 관계를 확인합니다.
2. 입력, 출력, 오류, 시간·RNG·월드 의존성을 정리하고 작은 대조 시나리오를 만듭니다.
3. Rust의 적절한 책임 영역으로 옮깁니다. 필요한 부분은 구조를 유지한 기계적 번역으로 시작할 수 있습니다.
4. 동일한 입력·시드·tick 순서에서 Java 기준과 상태·패킷·RNG 진행을 비교합니다.
5. 최적화는 별도 변경으로 평가합니다. 원래 Java 또는 Pumpkin의 최적화를 유지하는 번역도 같은 검증을 통과해야 합니다.
6. 출처·대응 심볼·검증 근거·의도한 차이·측정 결과를 형제 `Roadmap/PORTING.md`에 기록합니다.

## Java와 Rust의 차이를 확인할 항목

- 정수 overflow, signed/unsigned shift, 나눗셈·나머지, 부동소수점 NaN과 반올림.
- 객체 동일성, 별칭, nullable 상태, 컬렉션 순회 순서와 순회 중 변경.
- 상속·가상 호출, 초기화 순서, 예외 경로, 수명과 상태 소유권.
- 난수 알고리즘과 호출 횟수, seed 분리, tick 중 이벤트 순서와 예약 작업 순서.
- 패킷 길이·범위 검증, NBT 형식, 저장 데이터와 레지스트리 버전.

단순 텍스트 치환만으로 동등성을 판단하지 않습니다. 디컴파일 성공은 컴파일 가능성이나 동작 동등성의 증거가 아닙니다.
디컴파일러가 복원하지 못한 주석·원본 지역 변수 등은 바이트코드와 실행 관찰로 보완합니다.

## Pumpkin 활용

고정 커밋의 NBT·프로토콜·청크 저장·유틸리티를 후보로 살펴보고, 필요한 코드의 실제 의존성·완성도·버전 적합성을 평가합니다.
게임 동작의 기준은 해당 버전의 공식 Java 서버입니다. 원본에 구현이 존재한다는 사실만으로 대응 기능 완료를 표시하지 않습니다.
직접 가져오는 코드에는 upstream 경로·커밋과 원본 라이선스/저작권 표기를 함께 기록합니다.

첫 구현 목표는 수치/RNG/codec의 대조 검증 기반과 최소 서버 접속 흐름입니다.
플러그인 API, 여러 버전 동시 지원, Bedrock 지원은 현재 26.3 Java 서버 작업 범위에 넣지 않습니다.
