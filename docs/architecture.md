# Rust 이식 설계 초안

이 문서는 구현 전 설계 기준입니다. 아래 경계는 논리적 책임이며, 아직 Rust crate나 trait로 구현하지 않았습니다.
첫 기능에 필요한 경계부터 코드로 만들고 실제 의존 관계가 생길 때 crate를 분리합니다.

## 제품 제약과 우선순위

2026-09-05 추가 요구를 반영합니다. **청크 로딩·tick의 멀티코어 처리량과 지연 개선을 우선**하며,
이를 위해 측정 가능하고 상한이 있는 RAM 증가는 허용합니다. 메모리 효율은 최소 점유량만을 목표로 하지 않고
개선한 처리량·지연 대비 비용으로 평가합니다. 컴파일 시간과 구조의 단순성도 설계 판단에 포함합니다. 공격적인 최적화는 허용하지만 바닐라의 관찰 가능한
동작·패킷 순서·지원 범위를 심각하게 바꾸어 얻은 성능 향상은 채택하지 않습니다.
동작 보존은 성능 점수와 교환하는 항목이 아니라 채택 조건입니다.

- 코어 사용률 자체보다 동일 작업의 처리량, tick p95/p99, CPU 시간과 코어 수별 확장성을 평가합니다.
- RSS만 보지 않고 살아 있는 청크·엔티티·연결당 메모리, 큐·작업 중간 결과·캐시의 peak와 회수 지연을 측정합니다.
- 병렬성을 높이는 owned draft·snapshot·double buffer·worker scratch·동시 작업 수는 초기 비교 후보입니다.
  추가 RAM이 처리량·p99 지연을 개선하면 채택할 수 있지만 무제한 queue·cache·누수는 허용하지 않습니다.
- 시야·simulation distance, AI 주기, RNG 호출, 전송해야 할 패킷을 몰래 줄여 성능을 확보하지 않습니다.
- 호환성 결과가 같은 최적화도 RAM·처리량·지연·빌드 시간의 비용을 함께 기록합니다. 아직 측정한 성능 개선치는 없습니다.

## 지원 플랫폼

사용자가 확인한 범위는 모두 64-bit입니다. 아래는 지원 목표이며 현재 실제 서버 빌드·실행이 검증된 목록은 아닙니다.

| 운영체제·CPU | Rust target | 기본 방향 |
| --- | --- | --- |
| Linux ARM64 | `aarch64-unknown-linux-gnu` | glibc 기반 배포 |
| Linux x86_64 | `x86_64-unknown-linux-gnu` | glibc 기반 배포 |
| macOS Apple Silicon | `aarch64-apple-darwin` | ARM64 네이티브 |
| Windows x86_64 | `x86_64-pc-windows-msvc` | MSVC ABI |

32-bit, Intel Mac, Windows ARM64, Linux musl은 현재 기본 지원 범위가 아닙니다.
최소 OS/libc 버전과 Rust MSRV는 첫 CI·배포 기준을 고정할 때 명시합니다.
배포 바이너리에 `target-cpu=native`를 전역 적용하지 않습니다. SIMD·allocator·native codec은 네 플랫폼의
호환 경로를 유지하며 측정 후 선택합니다. 플랫폼별 대체 구현은 실제 차이가 생기는 입출력·최적화 경계에 한정합니다.

## 바닐라 호환 기준

기준은 잠금 버전 `26.3-pre-2`입니다. `ChunkMap.java:125,805-818`에서 서버 view-distance는 **2..32**로 제한되고,
플레이어 요청은 그 서버 범위 안으로 제한됩니다. 사용자는 이 범위를 그대로 지원하기로 확인했습니다.
`PlayerChunkSender.java:25-28,114-125`의 **0.01..64**는 요청된 chunks/tick 전송률이며 시야 반경이 아닙니다.
view distance, simulation distance, chunk ticket·generation 의존 범위를 같은 숫자로 취급하지 않습니다.

- 연결별 프로토콜 상태, 패킷 인과 순서, chunk batch의 start/data/finish/ack 경계를 보존합니다.
- 압축·암호화 상태 변경 전후의 bytes는 각각 올바른 상태로 처리합니다. 작업 완료 순서로 전송 순서를 정하지 않습니다.
- tick 단계의 관찰 가능한 효과, 예약 작업의 tie-break 순서, RNG 스트림과 엔티티·블록·유체의 상호작용을 보존합니다.
  Vanilla의 thread 배치·대기·자료구조 자체는 호환 계약이 아닙니다. 독립 계산의 내부 실행 순서·실행기는 적극 변경할 수 있습니다.
- 부하가 높아도 필수 패킷을 조용히 버리지 않습니다. byte 예산에 따른 생산 제한·역압과 명시적인 연결 종료 정책을 사용합니다.
- 여러 연결에 존재하지 않는 전역 패킷 순서를 새로 강제하지 않습니다. 대조 검증에서는 연결별 순서와 상태 전이·인과 관계를 검사합니다.

최적화별 원본 위치와 채택 조건은 [탐색·최적화 계획](optimization-plan.md)에 기록합니다.

## 책임과 의존 방향

| 영역 | 책임 | 의존 규칙 |
| --- | --- | --- |
| 공통 값·연산 | 좌표, 식별자, 수치·비트 연산, 시간 단위, RNG | 네트워크·파일·비동기 런타임에 의존하지 않음 |
| 게임 상태·규칙 | 월드·청크·블록·엔티티 상태, 이벤트와 tick 전이, AI | 공통 값과 명시적인 상태 접근 경계에 의존 |
| 서버 실행 조정 | 세션·월드 수명, tick 스케줄, 명령 실행, 입출력 결과 반영 | 게임 규칙을 호출하며 변경 적용 순서를 소유 |
| 외부 입출력 | 프로토콜 codec, 연결, 인증, 월드 저장, 설정 | 게임 내부 자료 구조를 wire/storage 형식과 구분 |
| 검증 도구 | Java 대조 실행, 상태 스냅샷, 재현 시나리오, 벤치마크 | 제품 코드가 검증 도구에 의존하지 않음 |

게임 로직에 `async`, 소켓, 파일 접근을 기계적으로 퍼뜨리지 않습니다. 게임 상태에 영향을 주는 외부 결과는 바닐라의 해당 실행 단계와
소유 경계에서 적용하고, 연결 상태 전이는 연결별 순서를 보존합니다. 병렬 tick은 초기 핵심 개발 항목이며 순서·의존성 검증과 함께 구현합니다.
Pumpkin의 `Arc`·락 구조나 병렬화 방식을 프로젝트 전체 구조로 그대로 복제하지 않습니다.

## 동기·비동기·병렬 실행 결정

`async`는 대기를 겹치는 방식이고 CPU 병렬 실행과 구분합니다. 게임 상태의 권위 있는 변경에는 동기적 소유 경계를 둡니다.
단일 스레드 경로는 대조 기준과 fallback으로 먼저 마련하고, **독립적인 tick 작업을 병렬 실행하는 경로를 P1~P2에서 함께 개발**합니다.
월드·지역·엔티티가 서로 다른 객체라는 이유만으로 독립적이라고 가정하지 않습니다. 같은 tick에서의 읽기/쓰기·이웃·RNG·전역 상태 의존성을
검증하여 병렬 실행 범위를 넓힙니다. 계산·입출력도 처음부터 다른 코어와 겹쳐 수행합니다.

| 작업 | 결정 | 적용·순서 경계 |
| --- | --- | --- |
| 소켓 read/write, 연결 수명, 타이머 | 비동기 I/O | 연결별 상태 소유, 제한된 수신/송신 버퍼 |
| 외부 인증·프로필 조회 | 비동기 I/O | timeout·취소, 세션 generation 확인 후 login 상태에 반영 |
| 프레이밍·작은 codec 연산 | 연결 담당 실행 흐름에서 동기 | 길이·범위 검사 후 순서대로 명령화 |
| 큰 패킷 압축/해제·직렬화 | 예산이 있는 CPU worker | immutable 입력, 상태 epoch/sequence, 순서 복원 후 출력 |
| 연결 암호화·실제 socket write | 연결별 순차 | 압축 결과 대기 순서와 cipher 상태 전이를 통합 |
| region 파일 read/write | 제한된 blocking I/O worker | region별 쓰기 순서, 저장 revision·durability 경계 |
| 청크 NBT 해석·인코딩·압축 | CPU worker | 소유된 draft/snapshot, 완료 후 최신 revision 검증 |
| noise·worldgen의 독립 계산 | CPU worker | chunk status·이웃 의존성·seed를 보존하는 작업 그래프 |
| light 계산 | 단계적으로 병렬화 | 이웃 경계·전파 완료·publish 순서를 검증한 뒤 활성화 |
| 패킷의 게임 상태 적용·명령·inventory·전투 | 동기 상태 변경 | 바닐라 처리 단계와 연결별 입력 순서 보존 |
| block/fluid/entity/AI/passenger tick | 동기 계산을 의존성 단위로 병렬 실행 | 독립성을 확인한 작업부터 P1~P2에 구현, 상호작용 영역은 원래 순서 유지 |
| AI·pathfinding의 읽기 계산 | 초기 병렬 실험 후보 | 같은 tick의 앞선 변경을 읽어야 하는지 검사, snapshot 비용·취소율·적용 순서 검증 |
| 저장·종료·reload | 비동기 준비 + 동기 전이 | quiesce, 작업 drain/cancel, 마지막 저장과 상태 전환 경계 |

CPU 작업은 서버 전체가 공유하는 **하나의 제한된 worker 예산**으로 관리합니다. 월드마다 코어 수에 비례하는 풀을 만들지 않습니다.
I/O runtime·CPU pool·blocking I/O의 runnable 수를 함께 계측하고, CPU가 적은 환경에서도 최소 스레드 수를 중첩 강제하지 않습니다.
작업마다 새 스레드를 만들거나 무제한 `spawn`/`spawn_blocking`으로 부하를 이동시키지 않습니다.
특정 executor crate·스레드 수는 P1 측정 기반에서 고정하며, executor를 교체하기 위한 범용 계층은 선행 구현하지 않습니다.

### tick 병렬화의 첫 구현 범위

1. 바닐라의 tick 단계·논리 순서와 단일 스레드 대조 경로를 만든다.
2. 선택한 tick 종류에 보수적인 읽기/쓰기 범위, 이웃 범위, RNG·전역 자원 의존성을 명시한다.
3. 상호작용하는 작업은 같은 실행 단위 또는 순서가 있는 의존 관계로 묶고, 독립적으로 실행 가능한 단위를 공용 worker에서 병렬 처리한다.
4. 동적 전파 범위를 증명하지 못하는 작업은 **상태를 바꾸기 전에** 동기 소유 경로로 보낸다. 경계 이벤트를 다음 tick으로 미루어 해결하지 않는다.
5. 같은 tick의 앞선 변경을 뒤 작업이 읽어야 한다면 그 의존 순서를 유지한다. 오래된 snapshot으로 병렬 계산한 뒤 commit 순서만 맞추는 방식은 충분하지 않다.
6. 독립 부하와 밀집 상호작용 부하에서 각각 비교한다. 충돌이 많은 영역이 직렬로 합쳐지는 비율, scheduler 비용과 RAM을 함께 측정한다.

초기에는 범용 transaction/MVCC/rollback 프레임워크를 만들지 않습니다. 특정 기능의 의존성 규칙으로 검증할 수 있는 작은 병렬 경로부터 도입합니다.
전체 mutable loop를 무조건 `par_iter`로 바꾸는 직접 이식을 피하면서, tick 병렬화 자체는 후반 작업으로 미루지 않습니다.

큐에는 작업 개수와 **입력+출력+중간 버퍼의 bytes 예산**을 함께 둡니다. 네트워크·generation·저장 큐가 각자 무제한 확장되지 않도록
예산을 배분합니다. 세션 종료·텔레포트·차원 이동·chunk unload 시 오래된 작업을 취소하거나 결과를 폐기하고 예산을 회수합니다.
결과 대기열도 제한합니다. 앞 작업이 느릴 때 뒤 결과가 RAM을 무한 점유하지 않게 생산을 제한합니다.
예산은 snapshot·압축 해제·출력 버퍼를 할당하기 **전**에 예약합니다. 취소된 worker도 실제 입력·출력 버퍼가 해제될 때까지 예산을 점유합니다.
stale 결과를 논리적으로 폐기한 시점과 실제 메모리 반환 시점을 구분하며, 재사용 pool의 retained capacity도 해당 pool 예산에 포함합니다.

## 컴파일 시간과 추상화

- 시작은 최소한의 Rust 구성으로 하고 코드 경계를 곧바로 많은 crate로 나누지 않습니다. 의존성·증분 빌드 효과로 분리 필요를 설명합니다.
- 기본은 구체적인 struct/enum과 명시적인 소유권입니다. trait는 실제 대체 구현이나 안정적인 테스트 경계가 있을 때 도입합니다.
- hot path의 generic은 필요 범위로 제한합니다. 광범위한 type parameter 전파·중복 monomorphization과 불필요한 derive/proc macro를 피합니다.
- 모든 곳의 `dyn` 제거 또는 모든 타입의 boxing을 목표로 삼지 않습니다. dispatch 비용, 코드 크기와 컴파일 시간의 실제 측정으로 결정합니다.
- 초기 Java 서버에는 플러그인 VM·WASM/WASI·Bedrock·관리 웹 서버를 함께 끌어오지 않습니다. Pumpkin workspace를 통째로 의존하지 않습니다.
- 개발 빌드는 incremental·빠른 반복을 우선합니다. 최초 release 비교는 Cargo 기본 설정을 기준으로 하며 fat LTO/단일 codegen unit을 기본 강제하지 않습니다.
- thin LTO, PGO, SIMD, allocator 변경은 배포 성능 실험입니다. 실행 성능·peak RSS·clean/incremental build 시간·링크 시간을 함께 기록합니다.

## 메모리 기본 원칙

균일 section의 단일 값 표현, immutable 레지스트리 공유, 수명이 정해진 버퍼 재사용을 먼저 검증합니다.
packed palette는 정확성·메모리 비교 기준으로 두고, 활성 chunk에는 dense/byte-indexed 또는 mixed 표현도 초기부터 비교합니다.
generation용 dense draft와 보관·전송용 packed 형태, section 단위 snapshot/COW/double buffering의 처리량·전환 비용·RAM을 함께 평가합니다.
RAM이 늘어난다는 이유만으로 Pumpkin의 dense 접근을 제외하지 않으며, 빠르다는 가정만으로 채택하지도 않습니다.
읽는 쪽마다 전체 청크를 복제하거나 플레이어별 동일 chunk bytes를 무제한 캐시하지 않습니다.
작업 snapshot은 필요한 범위만 소유하고, cache key는 protocol·compression·chunk revision 등 출력에 영향을 주는 상태를 포함합니다.
캐시와 slab/pool에는 eviction·회수 기준을 둡니다. `Arc`, atomics, lock, 작은 heap 객체를 모든 게임 필드에 기계적으로 붙이지 않습니다.

## 기계적 번역 절차

1. 잠금 파일의 Java 버전과 정확한 클래스·메서드, 읽기/쓰기 상태와 호출 관계를 확인합니다.
2. 입력, 출력, 오류, 시간·RNG·월드 의존성을 정리하고 작은 대조 시나리오를 만듭니다.
3. Rust의 적절한 책임 영역으로 옮깁니다. 필요한 부분은 구조를 유지한 기계적 번역으로 시작할 수 있습니다.
4. 동일한 입력·시드·tick 순서에서 Java 기준과 상태·패킷·RNG 진행을 비교합니다.
5. 최적화는 별도 변경으로 평가합니다. 원래 Java 또는 Pumpkin의 최적화를 유지하는 번역도 같은 검증을 통과해야 합니다.
6. 출처·대응 심볼·검증 근거·의도한 차이·측정 결과를 형제 `Roadmap/PORTING.md`에 기록합니다.

## Java와 Rust의 차이를 확인할 항목

- 정수 overflow, signed/unsigned shift, 나눗셈·나머지, 부동소수점 NaN과 반올림.
- 객체 동일성, 별칭, nullable 상태, 컬렉션 순회 순서와 순회 중 변경.
- 상속·가상 호출, 초기화 순서, 예외 경로, 수명과 상태 소유권.
- 난수 알고리즘과 호출 횟수, seed 분리, tick 중 이벤트 순서와 예약 작업 순서.
- 패킷 길이·범위 검증, NBT 형식, 저장 데이터와 레지스트리 버전.

단순 텍스트 치환만으로 동등성을 판단하지 않습니다. 디컴파일 성공은 컴파일 가능성이나 동작 동등성의 증거가 아닙니다.
디컴파일러가 복원하지 못한 주석·원본 지역 변수 등은 바이트코드와 실행 관찰로 보완합니다.

## Pumpkin 활용

고정 커밋의 NBT·프로토콜·청크 저장·유틸리티를 후보로 살펴보고, 필요한 코드의 실제 의존성·완성도·버전 적합성을 평가합니다.
게임 동작의 기준은 해당 버전의 공식 Java 서버입니다. 원본에 구현이 존재한다는 사실만으로 대응 기능 완료를 표시하지 않습니다.
직접 가져오는 코드에는 upstream 경로·커밋과 원본 라이선스/저작권 표기를 함께 기록합니다.

첫 구현 목표는 수치/RNG/codec의 대조 검증 기반과 최소 서버 접속 흐름입니다.
플러그인 API, 여러 버전 동시 지원, Bedrock 지원은 현재 26.3 Java 서버 작업 범위에 넣지 않습니다.
